# Anthropic integration (report highlights)

> **Status:** partial — works, but the API key is an environment variable rather than a
> managed credential, and failures are invisible · **Last verified:** 2026-08-02
>
> The two written summary banners at the top of an ongoing report are generated by a
> language model from that month's stored figures.

---

## For everyone

### Purpose

A practice reading a page of numbers still has to work out what the month meant. The
highlights banner says it in two or three sentences: what went up, what the reviews looked
like, which keywords moved.

There are two banners:

- **Highlights** — the general summary, on every ongoing report.
- **AI SEO update** — a second banner, only when the practice has AI visibility data that
  month.

### Who uses it

The practice reads it. Nobody writes it by hand and there is no review or approval step —
the text goes straight into the report.

### How it behaves

1. After all a month's figures are stored, they are handed to the model as structured data.
2. The model returns either a summary or an explicit "nothing to say".
3. If it returns text, it is saved with that month's report and shown at the top.
4. **First reports skip this entirely** — a baseline month has nothing to compare against,
   so it gets the setup narrative instead.

### The guardrails

Because this text goes to a client unreviewed, the model is constrained:

- **It may only reference figures already in that month's report.** It is given the stored
  numbers and nothing else — it cannot look anything up, and it is instructed never to
  invent a figure or comparison.
- **Two to three sentences maximum**, per banner.
- **If there is nothing genuinely positive to say, it must return nothing** rather than
  writing filler. An omitted banner is the intended outcome, not a failure.
- **The AI SEO banner is only written when AI data is present.**

### When data is missing

| Situation | What the client sees |
|---|---|
| No API key configured | No banners; rest of the report normal |
| The service is unavailable or errors | No banners; rest of the report normal |
| The model returns unparseable output | No banners; rest of the report normal |
| The model judges there is nothing positive | No banner — working as intended |
| It is a first report | No banner; the baseline narrative appears instead |

**This never blocks a report.** A missing banner is invisible to the practice — the section
simply is not there.

### FAQ

**Q: Who checks the text before a practice sees it?**
A: Nobody, currently. The guardrails are enforced by the instructions given to the model
and by only ever giving it that month's own figures.

**Q: Can it get a number wrong?**
A: It is instructed to use only the figures provided and given nothing else to work from,
which makes an invented number unlikely — but there is no automated check that every number
in the text appears in the data.

**Q: Our report has no highlights and we had a good month.**
A: Either the model judged there was nothing clearly positive, or the service was
unavailable. The two are indistinguishable from the report itself.

## For developers

### API reference

**Endpoint** `POST https://api.anthropic.com/v1/messages`
**Auth** `x-api-key` header, from **`ENV["ANTHROPIC_API_KEY"]`**
**Version header** `anthropic-version: 2023-06-01`
**Model** `claude-haiku-4-5`, `max_tokens: 400`

Haiku is the deliberate choice: this is grounded summarisation of a small structured
payload, not a task needing a larger model.

The system prompt carries the guardrails and demands strict JSON:

```
{"summary": string|null, "ai_seo_summary": string|null}
```

The user message is the report payload as JSON. The reply is read from
`content[0].text` and parsed again as JSON.

### The payload

Deliberately narrow — the model sees **only** what is already persisted on that month's
report, and `.compact` drops anything absent:

| Key | From |
|---|---|
| `practice_name`, `report_month` | The report |
| `traffic` | `total_visits`, `organic_visits`, `appointments_booked`, `estimated_revenue` |
| `citation` | `total_impressions`, `total_engagements` |
| `gbp` | `average_rating`, `total_reviews`, `new_positive_reviews`, `new_negative_reviews` |
| `keyword_gains` | **Only keywords that improved** — with previous and current position |
| `ai_visibility` | `overall_score`, `previous_score`, `google_rank`, `ai_rank` |

`keyword_gains` is pre-filtered in Ruby to improvements only, so the model is not left to
work out which movements were good.

### Field mapping

→ `ReportHighlight`

| Source | Column |
|---|---|
| `summary` | `summary_text` |
| `ai_seo_summary` | `ai_seo_summary_text` |
| `HighlightGenerator::MODEL` | `model_used` |
| `Time.current` | `generated_at` |

If **both** strings are blank, `ReportGenerator#sync_highlights` writes no row at all.

### Key files

| Path | Role in this feature |
|---|---|
| `app/services/highlight_generator.rb` | Prompt, payload construction, call, parsing |
| `app/services/report_generator.rb` | `sync_highlights` — skipped for first reports |
| `app/models/report_highlight.rb` | The stored banner text |
| `app/views/reports/_highlights.html.erb` | Renders both banners; omits each when blank |
| `test/services/highlight_generator_test.rb` | Blank-key path, parse failures, payload shape |

### Data

Writes `summary_text`, `ai_seo_summary_text`, `generated_at`, `model_used` on
`ReportHighlight`, which is unique per report.

`model_used` is stored so a future change of model is traceable in reports already sent.

### Failure modes

| Failure | Result | Recorded in |
|---|---|---|
| `ANTHROPIC_API_KEY` unset | Returns nils immediately, no HTTP call | **Nothing** |
| `Faraday::Error` | Warning logged, nils returned | **Rails log only** |
| Unparseable JSON | Warning logged, nils returned | **Rails log only** |
| Model returns null for both | No `ReportHighlight` row | Nothing — intended |

**None of these reach `report_generation_logs`.** Unlike the five data adapters, this
service is not part of the warnings channel, so a persistently broken key produces reports
with no banners and no trace in the generation log. That is the main operational weakness
here.

### Gotchas

- **It never raises.** Every failure path returns `{summary_text: nil,
  ai_seo_summary_text: nil}` so report generation always proceeds.
- **It is not an `Adapters::Base` subclass.** It builds its own Faraday connection and does
  not use `ConnectionBuilder`, so it has **no retry policy and no explicit timeouts** — a
  divergence worth closing.
- **The key comes from `ENV`, not from `AgencyConnection`.** It cannot be managed from the
  Connections page like every other credential.
- **Failures are invisible to MSP** — Rails log only.
- **Double JSON parse**: the API response is JSON, and the model's text content is itself
  JSON that must be parsed again.
- **First reports skip this**, so a first report never has a banner regardless of data.
- **The payload is the guardrail.** Widening it to pass more context directly weakens the
  "can only reference figures in the report" property.

### Not built yet

- **No validation that numbers in the output appear in the input.** The guardrail is
  instruction-only.
- **No human review step** before a practice sees the text.
- **No retries or timeouts** — unlike every other outbound call in the app.
- **Not managed as a credential**; no place in the admin panel.
- **Failures not surfaced** to the generation log or anywhere a human looks.

## Changing this feature

- **Never widen the payload beyond figures already persisted on that month's report.** The
  "cannot invent numbers" property depends entirely on what the model is given.
- **Keep "return null rather than filler" in the prompt.** An omitted banner is correct
  behaviour, not a failure to fix.
- **Keep it non-raising.** A summarisation outage must never block a report.
- **Keep storing `model_used`** so already-sent reports remain traceable.
